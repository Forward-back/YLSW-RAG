# 评测说明

评测体系的设计、指标定义、复现方法与当前基线。目标：任何改动都能被量化验证，任何评审都能复现数据。

---

## 1. 测试集

### 1.1 构成（140 题）

`test/produce_question/qa_testset_120.json`

| 类型 | 题数 | 说明 |
|---|---|---|
| 单文档 | 72 | 单文档细节问答 |
| 多文档-串行 | 12 | 有依赖链的多文档问题 |
| 多文档-并行 | 12 | 多实体并列/对比问题 |
| 数值计算 | 12 | 语料内数值提取与计算 |
| SQL 能力题（SQL_01~20） | 20 | 表数据查询，L1 精确取值 / L2 计数 / L3 分组聚合 / L4 复杂条件 / L5 语义结构 五档梯度；答案均先经 SQL 对库算真值再入题 |
| 安全类（提示词注入/SQL注入/纯闲聊） | 12 | 期望拒答或安全处理 |

每题标注：`id`、`类型`、`问题`、`引用文档id`（父文档文件名 + 子块 id）。

### 1.2 已知识别缺陷（评测口径注意事项）

- **子块 id 漂移**：子块 id 在清库重入后会变化，字段级评测不可靠——答案层评测已改用**文档级参考**（父文档名取全文）。
- **选择题选项缺失**：个别原题是选择题但选项文本未入库，已改为问答题面。
- **引用文档不全**：少数跨文档题的 gold 标注缺部分来源文档（如对比题少标一家银行手册），judge 会按不完整参考判罚——此类判罚需人工复核，不计入系统缺陷。

## 2. 评测层级

### 2.1 延迟评测（Stage_1 / 快速）

- `src/server_bench.py e2e`：三问覆盖单步/并行子问/多跳 foreach，输出端到端耗时。
- `full_eval` 响应自带 `timings` 字段，按阶段统计（规划改写/变体生成/检索四路/RRF/精排/parent/LLM 生成/总计）。

### 2.2 检索层评测（Stage_2）

`test/Stage_2/eval_retrieval.py`（47 题，剔除安全类）：

- **视角 1 分层召回**：RRF 融合后与精排后两条 Recall@K（K=1..20）曲线，定位边际递减拐点。
- **视角 2 排序质量**：正确文档在精排后的排名分布（中位排名、Top-1/Top-3 占比）。
- **视角 3 区分度**：相关/不相关 chunk 的 rerank 分数分布与 AUC-PR——评测精排阈值是否可用。
- **视角 5 精排贡献**：正确文档从 RRF 排名到精排排名的迁移矩阵。

同类工具：`eval_chunk_matrix.py`（分块参数矩阵实验）、`eval_noise.py`（上下文噪声衰减实验）。

> 历史数据：`test/Stage_2/SUMMARY.md`（2026-09 快照，采集于旧索引时代，仅作方法论参考；当前数据见 §3）。

### 2.3 答案层评测（Stage_3）

两步流水：

1. `full_eval.py`：串行采集 140 题答案 + timings + trace，落 `full_eval_result.json`。
2. `answer_judge.py`：LLM 裁判（DeepSeek 官方 API）按文档级参考判 正确/部分正确/错误。参考构建规则：
   - 按「父文档id」取当前库全文（规避子块 id 漂移）
   - xlsx 文档附 **tables_structured 聚合视图**（字段取值计数）——曾用原始行 JSON 导致 LLM "数不清数百行"误判（京珠 55/38 被数成 23/13）
   - 安全类 12 题直接判正确（拒答即正确）
   - 参考截断 25000 字符（长法规尾部条款、案例表曾因截断造成假阴性）

裁判输出 `answer_judge_result.json`，人工复核部分/错误题的判罚理由是否成立。

## 3. 当前基线（2026-10-24，140 题全量）

### 3.1 功能稳定性

| 指标 | 值 |
|---|---|
| 请求异常 | 0 / 140 |
| 空答案 | 0 / 140 |
| 超 30s | 0 / 140 |

### 3.2 质量

| 指标 | 值 | 口径 |
|---|---|---|
| 检索文档级 hit@10 | 100%（106/106） | full_eval trace 文档级判定（排除拒答题） |
| 答案正确率 | ~87%（正确 104 / 部分 13 / 错误 3） | 120 题 judge（含安全题；20 道 SQL 题单独判定 19 正确/1 部分） |
| 文档级 Recall@10（重排后） | 95.7%（47 题） | Stage_2 eval_retrieval |
| 正确文档中位排名 | 1 | Stage_2 视角 2 |

### 3.3 延迟（客户端端到端，140 题串行）

| 指标 | 值 |
|---|---|
| 平均 / 中位 | 8338 / 8486ms |
| p90 / p95 | 9808 / 10458ms |
| min / max | 3.6s / 11.9s |
| 服务端总计中位 | 6463ms |

分阶段中位：规划+变体（并行）1.9s、检索 0.9s、精排 1.8s、LLM 生成 1.7s。按类型：安全题（短路）3.6-3.9s、单文档 8.8s、多文档 8.4-9.2s、数值计算 7.7s。

## 4. 历史演进（2026-09 → 10）

| 阶段 | 关键改动 | 效果 |
|---|---|---|
| 09 月基线 | 四路检索 + 精排 + 规划器 | Recall@10 93.6%（文档级，旧索引）；judge 正确率 ~80% |
| 10-16 索引修复 | 发现旧索引与所有 embedding 源不同源（self_hit=NO），硅基权重全量重建 | 语义路首次真正生效；hit@10 100% |
| 10-17 生成层 | 要点拆解自查 + 时间线 CoT + 拒答分流（injection/chitchat） | judge 错误 8→2（原 8 道错误全部升部分正确以上） |
| 10 月检索 | BM25 文号 token 保护、ef_search 192、动态实体同步、文档摘要前置 | 纯文号查询精确命中；概述类答案要点覆盖提升 |
| 10 月 SQL | 模板链重构 + 列索引 + 语义选表 + few-shot + 连接自愈 | SQL 20 题 19 正确/1 部分（此前多项 50% 级） |
| 10 月延迟 | 变体并行 + 批量 embedding + 多路精排并行 + 空池短路 | 140 题平均 9642→8338ms，p90 13148→9808ms |

## 5. 复现方式

```bash
# 前置：服务已启动（见 README / 部署手册）
# 1. 全量答案采集（约 20 分钟）
python test/Stage_3/full_eval.py

# 2. LLM 裁判（需 DEEPSEEK_API_KEY 环境变量，约 2 分钟）
DEEPSEEK_API_KEY=<key> python test/Stage_3/answer_judge.py

# 3. 检索层专项（约 15 分钟）
python test/Stage_2/eval_retrieval.py

# 4. 端到端延迟基准
python src/server_bench.py e2e
```

产物：`full_eval_result.json`（答案+耗时+trace）、`answer_judge_result.json`（判定+理由）、`recall_at_k.json` / `pr_curve.json` / `rank_migration.json` 等。
